## 0. 개정 결론

이 계획의 **주제 선정, 안전 범위, 주차 간 연결, 방어·재시험 중심의 방향은 타당하다.** 다만 기존 `3.1 한 모듈의 기본 뼈대`를 모든 화면에 같은 순서와 같은 제목으로 적용하면, 내용이 맞더라도 강의 자료가 아니라 자동 생성된 카드 묶음처럼 보일 수 있다. 이번 개정에서는 다음 네 가지를 구현 기준으로 확정한다.

1. 기존 8단계는 화면에 그대로 노출하는 목차가 아니라, 저자가 빠뜨린 항목을 찾는 **숨은 편집 검수표**로 사용한다.
2. 실제 모듈은 원리 해설형, 흐름 추적형, 사례 판정형, 도구 관찰형, 방어·재시험형 중 하나를 택해 서로 다른 읽기 리듬을 만든다.
3. 외부 자료를 읽지 않아도 핵심 경로를 이해하도록, 선수 개념·용어·보충 개념을 사이트 내부의 개념 레지스트리와 접이식 보충 설명으로 연결한다. 외부 과정은 핵심 설명의 대체물이 아니라 학습 전이 단계다.
4. 분량보다 설명의 완결성을 우선한다. 특히 Week 10과 Week 13은 기존 총량이 공통 하한보다 작고, Week 11은 두 분야를 한 주에 묶어 과밀하므로 아래 보강 기준을 우선 적용한다.

> 이 문서에서 기존 주차별 표와 뒤의 “주차별 적합성 감사”가 충돌하면, **주차별 적합성 감사와 개정 분량**을 최종 구현 기준으로 삼는다.

## 1. 목적과 적용 범위

이 계획의 대상은 SecTrack 화면에서 보이는 **Week 03부터 Week 15까지**다. 목표는 짧은 정의와 문제 목록을 늘리는 것이 아니라, 보안을 처음 배우는 1학년이 다음 질문에 자기 말로 답할 수 있을 정도의 읽기 자료를 만드는 것이다.

1. 이 기술 또는 시스템은 원래 무엇을 하기 위해 존재하는가?
2. 데이터와 권한, 실행 흐름 중 어디에서 경계가 깨지는가?
3. 그 결함은 어떤 조건에서 실제 문제가 되며, 영향은 어디까지 가능한가?
4. 개발자와 운영자는 어떤 설계와 검증으로 이를 줄이는가?
5. 실습, 취약점 보고서, 재시험에서 무엇을 사실로 기록해야 하는가?

범위에는 보안의 배경, 방어 관점, 안전한 합성 예시, 로컬 실습, 외부 학습으로 넘어가는 다리가 포함된다. 승인되지 않은 대상에 대한 공격 절차, 원격 표적 자동화, 실제 계정·세션·키 탈취 예제, 재현 가능한 침해 지침은 포함하지 않는다.

### 2.1 사용자가 준 XSS 참고 글

#### 채택하지 않을 표현

- 한 페이지에 정의·종류·공격·방어를 모두 넣고 각 항목을 짧은 목록으로 끝내는 백과사전형 요약.
- 매 모듈이 `학습 질문 → 핵심 설명 → 관찰 흐름 → 흔한 오해 → 체크포인트 → 핵심 정리`라는 동일한 화면을 갖는 방식.
- “중요합니다”, “주의해야 합니다”, “보안을 강화할 수 있습니다”처럼 근거와 행동이 없는 문장.
- 실습 링크를 핵심 설명보다 먼저 노출하거나, 외부 플랫폼을 읽지 않으면 내부 본문을 이해할 수 없는 구조.
- 공격 성공 장면을 과도하게 강조하고 보호 장치·권한·환경 전제를 뒤에 작게 붙이는 구성.

#### SecTrack의 세 겹 문서 구조

1. **강의 서사층**: 학생이 처음부터 끝까지 읽는 본문. 상황, 원리, 실패, 판단, 수정이 자연스럽게 이어진다.
2. **개념 참조층**: 용어 카드, 선수 개념, 보충 설명, 공식 근거. 본문을 떠나지 않고 필요한 만큼만 펼친다.
3. **관찰·증거층**: 코드, 로그, 패킷, 메모리 지도, 정상/실패/수정 후 비교, 질문과 재시험 기록.

세 층을 같은 비중으로 한꺼번에 펼치지 않는다. 기본 화면은 강의 서사층을 보여 주고, 개념 참조층과 세부 증거는 학습자의 선택 또는 문맥상 필요한 시점에 확장한다.


### 2.4 현재 SecTrack 구현과 계획의 차이

2026-07-13 기준 저장소 구조를 계획과 대조하면, **기술 방향은 이미 상당 부분 반영됐지만 편집 구조와 깊이는 아직 계획 수준에 도달하지 않았다.**

#### 현재 구현의 강점

- 학습 경로가 개념 → 안전한 관찰 → 증거 → 이해 확인 → 보고서로 연결돼 있다.
- XSS는 payload 목록보다 source, transform, sink, context, retest를 중심으로 설계돼 있다.
- 로컬·합성 자료, sandbox, credential 마스킹, 허가된 외부 과정이라는 안전 경계가 코드와 문서에 반영돼 있다.
- `LessonRenderer`는 질문, 설명, diagram, code/HTTP, comparison, timeline, case, misconception, checkpoint, source 등 다양한 기본 block을 이미 지원한다.
- 모바일 터치 크기, 키보드 focus, 코드 줄바꿈, 표의 접근 가능한 영역 같은 기본 UI 품질은 양호하다.

#### 계획과의 핵심 격차

| 위치 | 현재 상태 | 개정 방향 |
| --- | --- | --- |
| `src/data/curriculum/week5to10.js` | `lesson()`이 모든 모듈에 질문, 설명, 일반화된 흐름도, 오해, 2개 checkpoint, 실습, 출처, 요약을 같은 순서로 삽입한다. | factory는 안전한 기본값만 제공하고, 모듈별 blocks와 서술 유형은 저자가 선택한다. |
| `src/data/curriculum/week11to16.js` | `learningModule()`도 거의 같은 순서를 반복한다. 주제는 바뀌지만 읽기 리듬이 같다. | 증거형, 도구형, 정책형, capstone형의 서로 다른 구조를 허용한다. |

| 주차별 후반 콘텐츠 | 구조화된 모듈과 합성 실습은 활성화됐지만 여러 주차가 현재 3~5개의 압축 모듈에 머물러 있다. | 이 문서의 5~7개 세부 모듈, 보충 개념, 종합 활동 기준으로 확장한다. |

| 공개 상태 문서 | `public/sectrack-context.md`의 구현 상태 설명이 최근 활성화된 후반 주차 코드와 어긋날 수 있다. | curriculum 변경과 같은 PR에서 README/context/roadmap 설명을 갱신한다. |

#### 구현 우선순위

1. Week 03 XSS 한 주만 먼저 새 서술 유형과 concept registry로 완성한다.
2. `lesson()`과 `learningModule()`의 고정 block 삽입을 제거하거나 선택형으로 바꾼다.
3. 기존 renderer에 `variant`, concept reference, evidence board, retest 표현을 추가한다.
4. Week 04~15를 확장하기 전에 콘텐츠 lint와 display week 매핑 테스트를 만든다.
5. XSS pilot을 초심자, 기술 검토자, 모바일 화면 관점에서 통과시킨 뒤 같은 원칙만 재사용한다. **화면 순서를 복제하지 않는다.**

이 판단에서 중요한 점은 “현재 사이트가 나쁘다”가 아니다. 기본 제품 구조와 안전 경계는 쓸 수 있다. 고품질 강의 자료로 보이게 만드는 데 필요한 변화는 **콘텐츠의 밀도, 개념 의존성, 제목, 사례 전개, 질문 위치를 주제별로 달리하는 것**이다.

## 3. 모든 주차에 적용할 콘텐츠 설계 규칙

### 3.1 한 모듈의 기본 뼈대: 화면 목차가 아닌 품질 계약

각 모듈은 독립된 블로그 글처럼 읽혀야 한다. 다만 아래 항목을 매번 같은 제목과 같은 순서로 노출하지 않는다. 이 항목은 저자와 리뷰어가 사용하는 **숨은 품질 계약**이다.

#### 3.1.1 모든 모듈이 답해야 하는 열 가지 질문

1. **어떤 장면에서 시작하는가**: 학습자가 이미 본 서비스, 코드, 오류, 로그, 패킷, 메모리 상태 중 하나를 제시한다.
2. **이 글을 읽고 무엇을 판단할 수 있어야 하는가**: “정의할 수 있다”보다 “두 흐름을 구분한다”, “증거를 보고 실패 지점을 고른다”처럼 관찰 가능한 완료 기준을 쓴다.
3. **읽기 전에 필요한 개념은 무엇인가**: 최대 3개를 표시하고, 사이트 내부의 짧은 복습 카드로 연결한다.
4. **새 용어와 정상 동작은 무엇인가**: 취약한 상태보다 먼저 정상 모델을 세운다. 용어는 처음 등장한 문장에서 정의한다.
5. **데이터·제어·권한은 어디로 이동하는가**: 주제에 맞는 흐름도, 메모리 지도, 요청 타임라인, 정책 평가도 중 하나로 나타낸다.
6. **어느 경계에서 약속이 깨졌는가**: 입력, 변환, 권한 검사, 출력, 저장, 메모리 접근, 도구 호출 중 실패 지점을 한 곳 이상 표시한다.
7. **무엇이 사실이고 무엇이 아직 추론인가**: 관찰 증거, 영향 판단, 필요한 전제, 미확인 항목을 분리한다.
8. **어떻게 고치고 운영 중 확인하는가**: 원인 수정, 보완 통제, 로그·경보, 테스트, 복구를 역할별로 설명한다.
9. **수정 후 무엇을 다시 비교하는가**: 정상 기준선, 실패 조건, 경계값, 다른 경로를 포함한 재시험을 제시한다.
10. **다음 학습으로 넘어갈 준비가 되었는가**: 내부 종합 활동 또는 허가된 외부 과정의 준비 조건과 제출물을 명시한다.

기존의 `상황 → 배경 원리 → 발생 지점 → 영향과 전제 → 방어 → 안전한 관찰 → Question → 재시험·외부 연결` 순서는 위 열 가지 질문 안에 그대로 남는다. 차이는 그것을 **화면의 고정 목차로 강제하지 않는 것**이다.

#### 3.1.2 모듈별로 택하는 다섯 가지 서술 유형

모듈은 아래 유형 중 하나를 주 유형으로 선택한다. 필요하면 보조 유형 하나를 더 쓸 수 있지만, 모든 유형을 한 모듈에 넣지 않는다. 한 주차 안에서는 최소 세 가지 유형을 섞고, 인접한 두 모듈이 완전히 같은 블록 순서를 갖지 않게 한다.

| 유형 | 화면에서 보이는 자연스러운 순서 | 잘 맞는 주제 |
| --- | --- | --- |
| **원리 해설형** | 익숙한 현상 → 핵심 질문 → 용어를 쓰며 정상 모델 설명 → 그림 → 작은 예시 → 오해 정정 → 한 문장 결론 | DB, Cookie, 포인터, 레지스터, 해시, IAM 용어 |
| **흐름 추적형** | 관찰할 입력·상태 → 단계별 이동 → 변환 지점 → 실패 지점 표시 → 안전한 경로와 비교 → 예측 질문 → 재시험 | XSS Source/Sink, SQL query, CSRF 요청, TCP 흐름, Agent tool call |
| **사례 판정형** | 짧은 사건 또는 합성 보고서 → 확인된 사실 → 가능한 가설 → 추가 증거 → 조건부 영향 → 판정 → 보고서 문장 수정 | 취약점 영향, 포렌식, PCAP, AI 답변 검증, 크래시 triage |
| **도구 관찰형** | 도구가 답하는 질문 → 화면·출력 읽는 법 → 한 단계 실행 → 출력 주석 → 흔한 오독 → 기록 양식 → 다음 관찰 | GDB, Wireshark, `readelf`, sanitizer, fuzzing dashboard |
| **방어·재시험형** | 수정 전 구조 → 근본 원인 → 코드·설정·권한 통제 → 수정 후 구조 → 정상/실패/회귀 시험 → 잔여 위험 | XSS/SQLi/CSRF 방어, 메모리 완화책, IAM 최소 권한, Agent 승인 게이트 |

#### 3.1.3 화면 제목은 내용에 맞게 쓴다

`핵심 설명`, `관찰 흐름`, `흔한 오해`, `핵심 정리` 같은 제목을 모든 모듈에 반복하지 않는다. 작은 UI 라벨로 유형을 표시할 수는 있지만, 실제 제목은 학습자가 지금 풀 질문을 드러내야 한다.

| 반복형 제목 | 권장 제목 예시 |
| --- | --- |
| 핵심 설명 | `문자열이 언제 HTML로 해석되는가` |
| 관찰 흐름 | `검색어가 URL에서 DOM까지 도달하는 경로` |
| 흔한 오해 | `HttpOnly가 막는 것과 막지 못하는 것` |
| 핵심 정리 | `보고서에 남겨야 할 네 가지 사실` |
| 다음 활동 | `이제 수정 전·후 DOM을 비교한다` |

제목만 읽어도 그 주차의 논리 흐름이 보이게 한다. 동일한 제목을 한 주차에서 두 번 이상 쓰지 않는 것을 기본 규칙으로 둔다.

#### 3.1.4 한 모듈의 실제 구성 예

**흐름 추적형 XSS 모듈**은 다음처럼 보일 수 있다.

1. `검색어는 언제 HTML이 되는가`라는 장면형 제목과 2문장 도입.
2. `Source`, `transform`, `sink`, `output context`를 흐름 그림 안에서 정의.
3. `[사용자 입력]`이 URL → 애플리케이션 → 응답 또는 클라이언트 코드 → DOM으로 이동하는 두 경로 비교.
4. 안전한 `textContent`와 해석형 `innerHTML`의 짧은 코드 비교.
5. “서버 응답에는 마커가 없고 실행 후 DOM에만 있다면 어디부터 확인할까?”라는 예측 질문.
6. 실행 관찰과 영향 판단을 분리한 합성 보고서 문장.
7. 정상 한글, 꺾쇠가 포함된 일반 텍스트, 빈 값, 다른 렌더링 경로를 포함한 재시험.
8. 관련 보충 개념인 DOM node, HTML parser, CSP를 필요한 위치에서 접어 볼 수 있게 연결.

이 예에서는 기존 8단계를 모두 충족하지만, 학습자에게 8개의 정형 카드로 보이지 않는다.

#### 3.1.5 Question은 끝에 몰아넣지 않는다

각 모듈에는 최소 두 개의 판단 장면을 둔다. 다만 둘 다 객관식 토글일 필요는 없다.

- **읽기 전 예측**: 그림이나 결과를 보기 전에 다음 상태를 예상한다.
- **중간 판정**: 제시된 증거만으로 확정할 수 있는 것과 없는 것을 구분한다.
- **수정 선택**: 같은 기능 요구를 유지하면서 근본 방어를 고른다.
- **재시험 설계**: 정상 기능과 실패 조건을 함께 검증할 입력·로그를 고른다.

주차 전체에는 최소 4개의 자동 피드백 가능한 확인과 1개의 종합 서술형 활동을 둔다. 정답 해설은 답만 말하지 않고, **왜 다른 선택지가 충분하지 않은지**까지 2~4문장으로 설명한다.

#### 3.1.6 모듈 작성자가 채우는 최소 메타데이터

| 필드 | 작성 기준 |
| --- | --- |
| `archetype` | 위 다섯 유형 중 주 유형 하나 |
| `learningQuestion` | 읽는 동안 계속 답할 한 문장 질문 |
| `observableOutcome` | 학습자가 실제로 할 수 있어야 하는 판정·설명·비교 |
| `prerequisiteConceptIds` | 이미 배운 개념 최대 3개. 내부 복습 링크 필수 |
| `newConceptIds` | 이 모듈에서 처음 정의하는 개념 |
| `evidenceObjects` | 코드, 로그, 요청, 패킷, 메모리, 정책 중 실제로 읽을 대상 |
| `failurePoint` | 실패 단계와 깨진 약속 |
| `impactConditions` | 권한, 기능, 데이터, 보호 장치, 환경 조건 |
| `controls` | 근본 수정, 보완 통제, 탐지·운영 통제 |
| `retestMatrix` | 정상, 실패, 경계값, 다른 경로 |
| `transferGate` | 다음 내부·외부 활동 전 확인할 준비 항목 |

이 메타데이터는 화면에 모두 노출하지 않는다. 콘텐츠 누락 검사와 주차 간 연결 자동화에 사용한다.

### 3.2 분량과 화면 구성의 공통 기준

- 주차의 **필수 본문**은 보통 8,000-11,000자를 목표로 한다. Week 03, 06, 09, 11, 12, 15는 9,500-13,000자까지 허용한다. 보충 개념·심화 읽기·표·코드 캡션·질문·출처는 필수 본문 분량과 별도로 집계한다.
- 모듈 하나의 필수 본문은 보통 **1,200-1,800자**다. 하나의 원리나 실패 지점을 설명하는 데 2,200자 이상 필요하면 모듈을 나누고, 900자 이하라면 독립 모듈이 필요한지 다시 검토한다.
- “모든 서브 개념을 설명한다”는 이유로 본문을 무한히 늘리지 않는다. 필수 이해에 필요한 개념은 본문에, 막힘을 해소하는 개념은 보충 카드에, 수학적·표준 세부는 심화 읽기에 둔다.
- 주차마다 최소 4개 시각 자료를 두되 숫자를 채우기 위한 장식은 금지한다. 최소 구성은 `전체 mental model 1개`, `실패 지점이 표시된 흐름 1개`, `정상/취약/수정 후 비교 1개`, `재시험 또는 증거 지도 1개`다.
- 다이어그램에는 반드시 “이 그림으로 답할 질문”과 1~3문장의 캡션을 둔다. 도형 색만으로 정상·실패를 구분하지 않고 텍스트 표지와 선 형태를 함께 사용한다.
- 주차마다 최소 2개의 오해 정정, 4개의 짧은 판단 장면, 1개의 종합 활동, 1개의 외부 전이 준비 체크를 둔다. 같은 형식의 객관식을 연속으로 배치하지 않는다.
- 표는 기본 3열 이하로 둔다. 네 가지 이상 속성을 비교해야 하면 카드, 탭, 접이식 목록, 두 개의 작은 표로 나눈다. 모바일에서 핵심 판단을 위해 가로 스크롤이 필수가 되지 않게 한다.
- 코드·명령·HTTP·패킷·정책은 “무엇을 보아야 하는지”를 줄 단위 주석으로 붙인다. 코드 블록 앞에는 관찰 질문, 뒤에는 관찰 결과와 한계를 둔다.
- 한 화면에 본문, 표, 코드, 질문, 경고가 모두 동시에 강조되지 않게 한다. 시각적 강조는 한 구간에 하나만 두고, 다음 구간과 24~40px 이상의 간격을 확보한다.
- 각 모듈 상단에는 `예상 읽기 시간`, `선수 개념`, `이 글에서 답할 질문`을 짧게 표시한다. 하단에는 `한 문장 결론`, `다음 모듈에서 다시 쓰는 개념`을 둔다.

### 3.3 안전성과 보고서 원칙

- 실습은 로컬, 의도적으로 취약하게 설계된 내부 화면, 또는 명확히 허가된 교육 플랫폼으로 제한한다.
- 취약점 보고서는 `관찰 사실`, `영향 판단`, `전제 조건`, `개선안`, `재시험 결과`를 분리한다. 추측을 사실처럼 쓰지 않는다.
- 민감 정보는 항상 가상값으로 사용한다. 실습 로그에는 쿠키, 토큰, 실제 계정, 개인 정보, 조직 주소를 보관하지 않는다.
- "방어"는 필터 하나나 제품 하나로 끝내지 않는다. 근본 원인, 보완 통제, 탐지·복구의 역할을 구분한다.


### 3.4 사이트만으로 이해되는 개념 계층

SecTrack의 핵심 경로는 외부 문서를 읽지 않아도 완결되어야 한다. 이를 위해 모든 주차에 다음 네 층을 사용한다.

1. **필수 본문**: 주차 완료 기준에 직접 필요한 설명. 외부 링크 없이 이해 가능해야 한다.
2. **보충 개념**: 본문을 읽다 막힐 때 30초~3분 안에 확인하는 정의·그림·짧은 예시.
3. **심화 읽기**: 표준 세부, 예외, 플랫폼 차이, 수학적 배경처럼 필수 완료 기준을 넘는 내용.
4. **외부 전이**: Dreamhack, Bandit, Fuzzing101, CloudGoat, 공식 문서에서 스스로 적용하는 단계.

#### 개념 레지스트리

모든 핵심·보충 개념은 한 번만 정의하고 여러 주차에서 재사용한다.

```js
{
  id: 'web-output-context',
  label: '출력 컨텍스트',
  english: 'output context',
  oneLine: '같은 문자열을 브라우저가 어떤 문법 위치에서 해석하는지 나타낸다.',
  firstIntroducedIn: 'w4-context',
  prerequisiteIds: ['html-dom-node', 'browser-parser'],
  relatedIds: ['safe-sink', 'contextual-encoding', 'html-sanitization'],
  commonMisconceptions: ['HTML escape 하나가 모든 위치를 보호한다.'],
  coreAnchor: '/learn/week/3#w4-context',
  sourceRefs: ['owasp-xss-prevention']
}
```

#### 첫 등장 규칙

- 약어는 처음에 한글 또는 전체 영어와 함께 쓴다. 예: `콘텐츠 보안 정책(Content Security Policy, CSP)`.
- 첫 문장에 사전식 정의만 놓지 않는다. “왜 지금 이 용어가 필요한지”를 같은 문단에서 설명한다.
- 이미 배운 개념은 한 문장으로 복습하고 원래 모듈로 연결한다. 같은 정의를 복사해 새 문장처럼 만들지 않는다.
- 선수 개념이 세 개보다 많으면 모듈을 쪼개거나 “시작 전 5분 복습”을 별도 제공한다.
- 보충 카드는 `한 줄 정의 → 작은 그림 또는 예시 → 지금 본문에서의 역할 → 관련 개념` 순서로 250~700자 안에 끝낸다.

#### 필수 경로와 심화 경로의 표시

- `필수`: 주차 완료 판정에 포함.
- `보충`: 이해가 막힐 때 확인. 완료율에는 포함하지 않음.
- `심화`: 관심 분야 확장. 기본 퀴즈에는 출제하지 않음.
- `외부 실습`: 제공자의 허가된 환경에서만 수행. 내부 준비 체크와 결과 기록이 필요.

학습자가 심화 카드를 읽지 않아도 다음 필수 모듈을 이해할 수 있어야 한다. 반대로 필수 본문에서 빠진 설명을 “자세한 내용은 공식 문서 참고”로 넘기지 않는다.

### 3.5 AI 티를 줄이는 편집·문체 규칙

AI처럼 보이는 가장 큰 원인은 사실 오류보다 **반복되는 리듬과 추상적인 문장**이다. 아래 규칙을 콘텐츠 리뷰에 적용한다.

#### 문장과 문단

- 한 문단은 한 주장만 다루고 3~5문장을 기본으로 한다.
- 첫 문장은 장면 또는 판단을 제시하고, 둘째 문장은 이유, 셋째 문장은 관찰 가능한 근거를 둔다.
- “~할 수 있습니다”를 연속해서 쓰지 않는다. 가능한 조건, 실제 동작, 확인 방법을 구체 동사로 바꾼다.
- “보안상 중요하다”, “주의가 필요하다”로 끝내지 않는다. 무엇을 확인하고 어떤 상태면 실패인지 적는다.
- 모든 목록의 항목 수를 3개로 맞추지 않는다. 내용에 필요한 만큼만 쓰되 7개를 넘으면 묶음을 만든다.
- 같은 문장 구조를 세 번 이상 반복하지 않는다. 설명, 짧은 질문, 코드, 그림 캡션, 사례 문장을 섞는다.
- 학생을 과도하게 지시하지 않는다. `외워라`보다 `이 두 줄을 비교하면 무엇이 달라졌는가`처럼 근거를 보게 한다.

#### 용어와 톤

- 초심자에게 정확한 용어를 숨기지 않되, 용어를 먼저 쌓아 놓고 뒤에서 설명하지 않는다.
- 한국어 용어를 주로 쓰고, 문서 검색에 필요한 영어를 첫 등장에 병기한다.
- 특정 제품명과 일반 원리를 구분한다. 예: `IAM 정책 평가`를 먼저 설명하고 AWS 예시는 그 다음에 둔다.
- `공격자라면`, `해커는`을 남발하지 않는다. 데이터, 권한, 구성 요소가 어떻게 움직이는지 중심으로 쓴다.
- 영향은 단정형 대신 조건형으로 쓴다. 단, 이미 관찰된 사실은 모호하게 흐리지 않는다.

#### 반복을 허용하는 것과 금지하는 것

- **허용**: `관찰 사실 / 영향 판단 / 전제 / 미확인`의 보고서 구분, 정상 기준선과 재시험 원칙, 안전 범위.
- **금지**: 모든 모듈 첫 문장의 “이 모듈에서는”, 모든 끝 문장의 “중요합니다”, 동일한 다섯 단계 화살표, 동일한 두 개 객관식, 동일한 3개 요약 bullet.

#### 저자 리뷰 질문

1. 이 문단은 실제 화면·코드·로그 없이도 다른 보안 주제에 그대로 붙일 수 있는가? 그렇다면 너무 추상적이다.
2. 제목만 바꾸면 다른 모듈과 구분되지 않는가? 그렇다면 고정 템플릿이 과하다.
3. 학습자가 무엇을 보았기 때문에 결론을 내리는지 한 문장으로 말할 수 있는가?
4. 예시가 앞의 원리를 검증하는가, 아니면 단순히 분위기를 만드는가?
5. 방어가 제품명·헤더명 나열에 머무르지 않고 실패 원인과 연결되는가?

### 3.6 시각 자료와 상호작용의 의미 체계

시각 자료는 종류에 따라 다른 질문에 답해야 한다.

| 시각 유형 | 답해야 하는 질문 | 필수 요소 |
| --- | --- | --- |
| 흐름도 | 값이나 요청이 어디서 어디로 이동하는가 | 시작점, 변환, 신뢰 경계, 실패 지점, 관찰 지점 |
| 메모리 지도 | 어떤 값이 어느 영역과 수명을 갖는가 | 객체 이름, 범위, 수명, 읽기/쓰기 방향 |
| 권한 지도 | 누가 어떤 자원에 어떤 조건으로 행동하는가 | 주체, 자원, 정책, 허용/거부, 유효 권한 |
| 타임라인 | 어떤 사건이 어떤 순서와 시간 기준으로 관찰되는가 | 시각, 출처, 사건, 불확실성 |
| 정상/취약/수정 비교 | 한 번의 수정으로 무엇이 달라졌는가 | 동일한 입력, 바뀐 한 요소, 결과, 회귀 확인 |
| 증거 보드 | 어떤 결론을 어떤 근거가 지지하는가 | 관찰, 출처, 해석, 미확인, 다음 확인 |

상호작용은 클릭 수를 늘리기 위해 넣지 않는다. 사용자의 선택이 그림, 결과, 기록 중 하나를 실제로 바꿔야 한다. 단순히 다음 카드를 여는 버튼은 일반 문서 흐름으로 대체한다.

### 3.7 콘텐츠 제작·검수 순서

1. 학습 완료 기준과 선수 개념을 먼저 확정한다.
2. 정상 동작의 mental model과 한 개의 누적 합성 사례를 만든다.
3. 실패 지점, 영향 조건, 방어, 재시험을 같은 사례에 연결한다.
4. 본문을 쓴 뒤에 제목을 정한다. 템플릿의 기본 제목을 그대로 두지 않는다.
5. 그림과 코드는 문장을 반복하지 않고, 문장만으로 보기 어려운 관계를 보여 준다.
6. 초심자 검토에서 막힌 용어를 보충 개념으로 승격한다.
7. 기술 검토에서 공식 출처, 조건부 영향, 보호 장치의 한계를 확인한다.
8. 모바일·키보드·스크린리더·긴 코드·긴 한글 단어를 포함해 화면을 검증한다.
9. 마지막으로 금지된 공격 문자열, 실제 비밀, 조직 식별자, 과장된 영향 문장을 점검한다.

## 4. Week 03-15 주차별 구현 명세

### Week 03. XSS: 브라우저가 데이터를 코드로 해석할 때

**학습 완료 기준**: 학습자는 반사형, 저장형, DOM 기반 XSS를 입력 위치가 아니라 **데이터가 위험한 출력 지점(sink)에 도달하는 경로**로 구분하고, HTML·속성·URL·JavaScript 컨텍스트마다 방어가 달라진다고 설명할 수 있다. 또한 보고서에서 "실행되었다"는 관찰과 "어떤 영향이 가능한가"라는 판단을 분리해 쓴다.

| 모듈 | 구체적으로 가르칠 내용 | 표현·실습 방식 | 목표 분량 |
| --- | --- | --- | --- |
| 03-1. 브라우저는 왜 문자열을 해석하는가 | HTML, DOM, JavaScript, origin, 렌더링의 역할. 서버 응답과 브라우저가 이후 DOM을 바꾸는 일을 분리한다. `<script>` 자체를 모르던 학습자도 태그·속성·텍스트 노드의 차이를 따라오게 한다. | 요청→응답→DOM 파싱→화면 표시 4단계 그림. 모든 위험 문자열은 `[사용자 입력]`으로 치환한다. | 1,500자 |
| 03-2. Source, transform, sink | URL·폼·저장 데이터가 source가 될 수 있고, 조합·템플릿·클라이언트 코드가 변환 단계이며, `innerHTML`류의 해석 지점이 sink가 되는 구조. 반사형·저장형·DOM 기반의 차이를 같은 도식 위에서 비교한다. | 데이터 흐름 지도와 3열 비교표. 안전한 `textContent` 대 해석형 출력의 합성 코드 비교. | 1,600자 |
| 03-3. 출력 컨텍스트가 방어를 바꾸는 이유 | HTML 본문, 인용된 속성, URL 값, JavaScript 문자열, CSS 값은 브라우저의 파서가 다르다. 프레임워크 기본 escaping, 컨텍스트별 encoding, 허용 HTML이 필요한 경우 sanitization을 구별한다. | 컨텍스트 색상 지도와 "이 출력 위치에서는 무엇을 데이터로 취급해야 하는가" 카드. | 1,700자 |
| 03-4. 왜 문제이고 무엇이 가능한가 | 피해자 브라우저의 동일 출처 문맥에서 UI 조작, 사용자의 권한으로 수행되는 동작, 민감 데이터 노출 같은 영향을 조건부로 설명한다. `HttpOnly`가 일부 쿠키 접근을 줄이지만 XSS 실행 자체를 해결하지 않는다는 점도 포함한다. | 영향 행렬: 사용자 권한 / 기능 / 보호 장치 / 가능한 결과. 과장된 "쿠키 탈취 = 모든 XSS" 오해 정정. | 1,300자 |
| 03-5. 설계·구현·브라우저의 방어 계층 | 기본 템플릿 escaping, 안전한 sink, 제한된 HTML sanitization, URL allowlist, CSP와 Trusted Types의 보완 역할, 라이브러리·프레임워크 escape hatch 점검. CSP·WAF·입력 차단만으로 해결된다는 오해를 바로잡는다. | 방어 계층 그림과 수정 전/후 코드 리뷰 카드. 실제 우회 문자열은 사용하지 않는다. | 1,700자 |
| 03-6. 보고서를 읽고 쓰는 법 | 제목, 범위, 재현 전제, source/sink/context, 관찰 결과, 영향, 원인, 권고안, 수정 후 재시험. 공개 보고서는 "공격 코드"보다 사실을 재현 가능하게 남기는 문서라는 점을 설명한다. | 합성 XSS 보고서의 좋은 문장/나쁜 문장 비교. | 1,300자 |
| 03-7. 수정 후 무엇을 다시 확인하는가 | 정상 텍스트가 깨지지 않는지, 모든 렌더링 경로가 같은 보호를 적용하는지, 허용 HTML 정책이 필요한 기능을 망가뜨리지 않는지, DOM 경로가 남지 않았는지 확인한다. | 샌드박스의 source/sink 추적 활동, Question 3개, Dreamhack으로 넘어가기 전 준비 체크. | 1,100자 |

- **주차 총량**: 본문 10,200자 내외, 흐름도 4개, 코드 비교 3개, 내부 XSS 샌드박스 1개, 보고서 읽기 활동 1개.
- **구현 방향**: `w4-*` 블록을 새 구조로 재편한다. 기존 XSS 샌드박스는 외부 통신·실제 세션을 사용하지 않는 상태를 유지하고, 출력 컨텍스트 선택과 source→sink 추적을 추가한다.
- **완료 판정**: `textContent`와 해석형 HTML 삽입의 차이, 유형별 데이터 경로, CSP의 보조적 성격, 수정 후 재시험 항목을 묻는 테스트를 통과해야 한다.

### Week 04. SQL Injection: 질의 코드와 데이터의 경계

**학습 완료 기준**: 학습자는 데이터베이스가 필요한 이유와 SQL 질의의 구성 요소를 이해하고, 문자열 조합이 왜 질의 구조를 바꾸게 만들 수 있는지 설명한다. 방어의 중심이 "특수문자 차단"이 아니라 매개변수화와 권한 최소화임을 안다.

| 모듈 | 구체적으로 가르칠 내용 | 표현·실습 방식 | 목표 분량 |

#### Week 03. XSS — 기준 품질로 삼되 선수 개념을 본문 안에서 복원한다

- 첫 화면에 HTML tag, attribute, text node, DOM, origin을 5분 복습 카드로 제공한다. “이전 주차에서 배웠다”는 이유만으로 생략하지 않는다.
- 반사형·저장형·DOM 기반을 입력 위치의 목록으로 가르치지 않는다. 같은 `source → transform → sink → context → browser interpretation` 지도에서 경로만 바꿔 비교한다.
- 출력 컨텍스트는 HTML body, quoted attribute, URL, JavaScript string을 필수로 하고 CSS는 심화로 둔다.
- `encoding`, `escaping`, `sanitization`, `validation`, `safe sink`를 서로 대체 가능한 용어처럼 쓰지 않는다.
- 영향 카드에는 사용자 권한, 기능 범위, 데이터 민감도, HttpOnly, CSP, 브라우저 격리 조건을 표시한다.
- 보고서 모듈은 나쁜 문장과 좋은 문장의 비교만 하지 말고, 학습자가 사실·영향·전제·원인·수정·재시험을 직접 재배열하는 활동을 포함한다.

**필수 보충 개념**: HTML parser, DOM node, origin/SOP, server response와 live DOM의 차이, output context, safe sink, sanitization policy, CSP의 보완적 성격.

#### Week 04. SQL Injection — SQL을 모르는 학생이 질의 경계를 볼 수 있게 한다

- 테이블·행·열·기본키·관계의 정의 다음에 “애플리케이션이 DB에 묻는 질문”이라는 관점으로 query를 설명한다.
- `SELECT ... WHERE ...`의 최소 문법을 색상으로 나누되, SQL 문법 강의로 확장하지 않는다.
- 값(value)과 식별자(identifier)를 분리한다. prepared statement가 값은 바인딩하지만 테이블명·정렬 방향 같은 구조는 그대로 매개변수화하지 못한다는 점을 allowlist와 연결한다.
- ORM을 자동 안전 장치로 묘사하지 않는다. 일반 API와 raw query 또는 문자열 기반 확장 지점을 비교한다.
- 영향은 DB 계정 권한, 읽기/쓰기 기능, 다중 문장 허용, 오류 처리, 백업·복구 상태에 따라 달라진다고 표시한다.
- 로그 예시는 질의 전체와 사용자 비밀을 무조건 저장하지 않고, request ID·query template ID·오류 분류·처리 시간을 남기는 운영 관점으로 만든다.

**필수 보충 개념**: relational database, schema, query, placeholder, bind parameter, value와 identifier, transaction의 기본 의미, ORM escape hatch, DB service account.

#### Week 05. CSRF — 브라우저가 자동으로 보내는 자격 증명이 전제임을 먼저 보여 준다

- 같은 요청 본문이라도 Cookie 기반 session, Authorization header, 명시적 credential 설정에 따라 CSRF 전제가 달라지는 비교를 넣는다.
- same-origin과 same-site를 별도 그림으로 설명한다. SameSite를 Origin 검증과 같은 것으로 쓰지 않는다.
- 인증(authentication), 인가(authorization), 요청 정당성(request authenticity)을 한 요청에서 각각 어느 단계가 확인하는지 표시한다.
- CORS는 브라우저의 교차 출처 응답 읽기 정책이며 CSRF 방어 그 자체가 아니라는 오해를 다룬다.
- token의 발급, 세션 연결, 전송, 검증, 회전·만료를 한 수명주기로 보여 준다.
- 고위험 변경에는 token 외에도 재인증, 사용자 확인, 거래 단위 승인, 감사 로그가 필요한 이유를 별도 사례로 둔다.

**선택 심화**: login CSRF, Fetch Metadata의 요청 헤더, SPA에서 credential mode, signed double-submit의 전제.

#### Week 06. C·컴퓨터 구조·메모리 — 필수와 심화를 나누지 않으면 과밀하다

- 필수 경로는 `byte와 값 → 주소와 포인터 → 배열·수명 → build pipeline → process memory map → 함수 호출 준비`로 제한한다.
- endianness, signed/unsigned 변환, alignment, undefined behavior는 보충 카드로 제공하되 Week 07과 Week 09 전에 반드시 한 번 복습한다.
- 포인터를 주소 숫자로만 설명하지 않는다. 가리키는 자료형, 유효 범위, 객체 수명, 접근 권한을 함께 표시한다.
- text/data/bss/heap/stack을 고정 주소 지도처럼 그리지 않는다. 역할과 상대적 개념, 환경에 따른 배치 차이를 명시한다.
- 전처리·컴파일·어셈블·링크·로딩 단계에서 입력과 산출물, 관찰 도구를 각각 하나씩만 제시한다.
- 같은 20~30줄 C 프로그램을 Week 07~09까지 계속 사용한다. 매주 새 프로그램을 도입하지 않는다.

**개정 목표 분량**: 필수 9,500-10,500자, 보충 2,000-3,000자.

#### Week 07. x86-64 어셈블리·호출 규약 — “정답 어셈블리 한 벌”처럼 보이지 않게 한다

- Intel/AT&T 표기 차이는 심화 카드로 두고 본문은 한 표기법으로 일관한다.
- instruction pointer, flags, register/memory/immediate를 먼저 구분한 뒤 분기와 call로 넘어간다.
- prologue, frame pointer, stack frame이 최적화와 컴파일러 옵션에 따라 달라질 수 있음을 실제 두 전사의 차이로 보여 준다.
- System V AMD64 ABI의 인자 레지스터를 암기표로 끝내지 않고 caller와 callee 사이의 책임으로 설명한다.
- stack alignment와 red zone은 필수 완료 기준이 아니라 “왜 디버거 화면이 교재 그림과 다를 수 있는가”라는 심화에 둔다.

**필수 보충 개념**: instruction pointer, flags, little-endian recap, memory operand, caller-saved/callee-saved, debug symbols와 optimization.

#### Week 08. GDB·pwntools — 도구 명령보다 관찰 질문을 우선한다

- 각 명령 옆에 “이 명령이 답하는 질문”을 표시한다. 예: breakpoint는 함수 도달 여부, step은 다음 명령 뒤 상태 변화를 확인한다.
- 소스, debug symbol, optimization, PIE/ASLR에 따라 주소와 화면이 달라지는 이유를 환경 manifest와 연결한다.
- pwntools는 bytes와 text, local process I/O, timeout, 로그, fixture 재현에 필요한 최소 기능만 다룬다.
- “pwntools는 공격 도구가 아니다”라고 단정하지 않는다. 다양한 대상과 연결 가능한 프레임워크이지만 과정에서는 로컬·허가된 환경만 쓴다고 정확히 적는다.
- 실습 기록에는 OS/architecture, binary hash, build option, 실행 명령, 입력 fixture, 관찰 시점을 포함한다.

**필수 산출물**: `환경 manifest + 관찰 명령 + 핵심 출력 + 해석 + 미확인 항목`.

#### Week 09. 메모리 안전성과 BOF 방어 — BOF를 대표 사례로, 원리는 더 넓게

- 메모리 안전을 bounds, lifetime, initialization, type/ownership의 네 관점으로 시작한다.
- stack buffer overflow 외에 out-of-bounds read/write, use-after-free, integer truncation을 한 화면짜리 비교로 소개한다. 실제 악용 절차는 넣지 않는다.
- crash, memory corruption, control-flow effect, exploitability, business impact를 한 단계씩 구분한다.
- safe API라는 표현은 함수명 목록으로 끝내지 않고 destination capacity, truncation, termination, error handling의 계약을 설명한다.
- sanitizer, compiler hardening, canary, NX, ASLR, PIE를 원인 수정과 분리한다. 어느 층에서 어떤 실패를 어렵게 만드는지 표시한다.
- 회귀 시험은 `0`, `1`, `capacity-1`, `capacity`, `capacity+1`, multi-byte input, empty input을 포함한다.

**권장 제목 조정**: `메모리 안전성과 경계 검사: BOF를 사례로 읽기`.

#### Week 10. AI 답변 검증형 Pwn 분석 — Week 08과 다른 산출물을 만든다

- Week 08이 “도구로 관찰하는 법”이라면 Week 10은 “주장을 검증 가능한 단위로 바꾸는 법”이어야 한다.
- 모듈을 `AI의 역할과 한계 → 환경 manifest → 주장-증거 원장 → 반례·거짓 전제 확인 → 안전한 재시험 → 보고서` 순서로 재구성한다.
- 각 AI 문장을 `직접 관찰`, `합리적 추론`, `추가 확인 필요`, `환경상 검증 불가`로 분류한다.
- 주소, 보호 기법, 함수 동작, 성공 조건처럼 환경 의존적인 값은 AI 답변에서 복사하지 않고 도구 출력과 파일 정보로 다시 확인한다.
- AI가 잘못된 함수명이나 존재하지 않는 옵션을 전제로 답했을 때 중단하고 전제를 검증하는 “false-premise check”를 넣는다.
- 결론에는 신뢰도 숫자보다 근거와 미확인 항목을 남긴다.

**개정 목표 분량**: 7,400-8,000자. 6개 모듈로 재구성하고, 환경 manifest와 주장-증거 원장을 독립 활동으로 둔다.

#### Week 11. 암호 기초·디지털 포렌식 — “무결성”을 두 분야의 연결 축으로 쓴다

- 암호 파트의 범위를 수학적 증명이나 알고리즘 구현이 아니라 “어떤 보안 속성을 어떤 primitive와 운용 조건으로 얻는가”로 제한한다.
- encoding, hashing, encryption, MAC, signature 뒤에 salt, password KDF, nonce/IV, authenticated encryption을 필수 보충으로 추가한다.
- “AES를 쓴다”보다 mode, key, nonce/IV, authentication tag, key lifecycle이 결과를 좌우한다는 점을 개념적으로 설명한다.
- 포렌식 파트는 수집 → 보존 → 무결성 확인 → 분석 → 타임라인 → 보고의 순서로 제한한다.
- hash 일치는 같은 바이트라는 근거이지 파일의 출처, 작성자, 의도, 사건 원인을 증명하지 않는다는 문장을 반복 검증한다.
- 시간대, clock skew, log retention, source reliability를 타임라인 카드에 포함한다.
- 법률·조직 절차는 관할과 조직에 따라 달라질 수 있으므로 일반 원칙과 수업 범위를 명시한다.

**개정 모듈 권고**: `11-1 보안 속성`, `11-2 primitive 비교`, `11-3 salt/KDF/nonce/AEAD`, `11-4 키와 위협 모델`, `11-5 증거 보존`, `11-6 타임라인과 한계`, `11-7 종합 활동`.

#### Week 12. 네트워크·PCAP·Wireshark — 패킷보다 관찰 지점을 먼저 정한다

- 캡슐화 그림에 MAC address, IP address, port, 5-tuple을 각 계층의 식별 정보로 표시한다.
- NAT가 인증·인가·암호화와 같은 보안 통제가 아니라 주소 변환·상태 관리 메커니즘임을 분명히 한다.
- TCP packet 한 개와 application stream 전체를 구분하고, retransmission·out-of-order·reassembly가 화면에 미치는 영향을 소개한다.
- TLS가 payload를 보호해도 IP, port, timing, size, handshake metadata 일부가 관찰될 수 있음을 과장 없이 설명한다.
- capture filter와 display filter의 차이 외에 “어디서 캡처했는가”가 증거 범위를 바꾼다는 capture point bias를 넣는다.
- 포트 번호만으로 서비스나 공격을 확정하지 않는 판단 문제를 최소 두 개 둔다.
- CAN은 차량·OT로의 확장 사례이므로 선택 심화 또는 Side Quest로 이동한다. 필수 네트워크 완료 판정에는 넣지 않는다.

#### Week 13. 퍼징 — 입력 생성보다 oracle과 triage를 포함한다

- 퍼징을 `input generation + execution + observation oracle + feedback + triage`의 시스템으로 정의한다.
- harness에는 deterministic behavior, global state reset, filesystem/network side effect 격리, timeout, resource limit가 필요한 이유를 넣는다.
- coverage 증가는 새로운 코드에 도달했다는 뜻이지 보안 결함 발견이나 correctness를 자동으로 뜻하지 않는다.
- sanitizer는 증상을 더 잘 보이게 하는 관찰 도구이며 영향 판정 자체가 아니라는 점을 crash log 활동에서 확인한다.
- 재현, stack trace 비교, 중복 제거, 최소화, root cause grouping을 triage 순서로 추가한다.
- 최소 입력은 공격 payload가 아니라 회귀 시험 fixture로 저장하고, 수정 후 동일 fixture와 정상 corpus를 함께 실행한다.

**개정 목표 분량**: 7,600-8,400자. `oracle`, `determinism`, `minimization/deduplication`이 빠진 원안은 구현 완료로 판정하지 않는다.

#### Week 14. 클라우드·IAM — 공급자 중립 원리와 AWS 실습을 분리한다

- cloud account/project, region, resource, control plane, data plane을 먼저 설명한다.
- shared responsibility는 서비스 모델뿐 아니라 사용한 managed service와 설정에 따라 달라지는 동적인 경계로 그린다.
- principal, identity, role, policy, action, resource, condition, explicit deny, effective permission을 하나의 정책 평가 흐름으로 연결한다.
- identity policy 외에 resource policy와 조직 수준 제한이 유효 권한에 영향을 줄 수 있다는 사실은 심화로 소개한다.
- 사람 사용자와 workload identity, long-lived key와 temporary credential을 비교한다.
- CloudGoat 준비 체크에는 전용 학습 계정, 결제 수단·예산 경보, region 확인, 민감 자원 없음, 배포 전후 inventory, destroy 후 검증을 포함한다.

**필수 산출물**: `요청 주체 → 정책 평가 → 유효 권한 → 로그 출처 → 제거 확인` 한 장 지도.

#### Week 15. AI/LLM/Agent 보안 — 앞 주차의 개념을 다시 쓰는 종합 위협 모델

- 모델, application layer, RAG, agent loop, tool, connector, memory, identity, policy enforcement point를 구분한다.
- prompt injection은 금지어 우회 문제가 아니라 신뢰할 수 없는 내용이 지시처럼 해석되는 시스템 경계 문제로 설명한다.
- 직접 입력과 문서·웹·메일에서 들어오는 간접 입력을 다른 데이터 경로로 그린다.
- tool allowlist만으로 끝내지 않고 argument validation, user confirmation, least privilege, transaction boundary, rate limit, sandbox, audit log를 조합한다.
- RAG data poisoning, sensitive retrieval, cross-tenant memory, model·dataset·plugin provenance, output handling을 데이터 수명주기로 묶는다.
- 평가에서는 공격 문구 모음보다 자산·행위자·경계·실패·통제·잔여 위험·증거를 정의한 test case를 만든다.
- 마지막 활동은 Week 03의 source/sink, Week 05의 요청 정당성, Week 09의 완화책, Week 14의 유효 권한, Week 10의 주장-증거 구분을 모두 재사용한다.

**완료 산출물**: 합성 Agent 서비스의 threat model, control matrix, 세 개의 안전한 eval case, 관찰 로그와 잔여 위험.

### 5.2 주차 시작 전 자동 선수 개념 확인

각 주차 상단에서 3~5개의 선수 질문을 제공하되 점수화하지 않는다. 오답이면 외부 링크가 아니라 2~5분짜리 내부 복습 카드로 이동한다.

예시:

- Week 07 시작 전: 값과 주소의 차이, stack과 heap의 역할, 함수 인자와 반환값.
- Week 12 시작 전: byte와 text의 차이, HTTP request/response, 로그의 관찰 시점.
- Week 15 시작 전: trust boundary, authentication/authorization, least privilege, evidence와 inference.

복습을 완료해도 주차 진행률을 부풀리지 않는다. 이는 학습 결손을 찾는 장치이지 별도 성취 항목이 아니다.

## 6. 구현 단계와 검증 게이트

### Phase A. Week 03 XSS를 기준 품질로 재구성

1. `w4-*` 콘텐츠를 7개 모듈 순서로 교체 또는 추가한다.
2. source→transform→sink, 출력 컨텍스트, 방어 계층, 보고서·재시험을 각각 독립 block으로 만든다.
3. 기존 내부 XSS 실습이 외부 통신, 실제 credential, 공격 payload를 쓰지 않는지 다시 확인한다.
4. 콘텐츠 스키마 테스트, XSS 안전성 테스트, 데스크톱·모바일 Playwright 화면 검증, production build를 실행한다.

### Phase B. Week 04-05 웹 보안의 깊이와 연결 보정

1. SQLi와 CSRF의 기존 상세 블록을 위 표의 목표 분량과 용어 수준에 맞춰 확장한다.
2. SQLi의 parameterization과 CSRF의 token은 "기능 이름"이 아니라 "서버가 확인하는 사실" 중심으로 재작성한다.
3. XSS가 있으면 CSRF 통제가 약화될 수 있다는 관계를 한 번만 정확히 연결하고, 과도하게 반복하지 않는다.
4. 각각 내부 관찰 활동, Question, 보고서 템플릿을 테스트한다.

### Phase C. Week 06-09 시스템 기반을 누적형으로 구현

1. 같은 작은 C 프로그램을 C 문법→메모리→어셈블리→GDB→메모리 안전성으로 재사용한다.
2. 주차별 화면에서 같은 그림을 복붙하지 않고, 이전 그림의 일부를 다시 보여 주며 새 관찰 요소만 강조한다.
3. BOF는 방어와 원인 분석을 중심으로 다루며, 실제 침해용 exploit tutorial로 바꾸지 않는다.
4. 코드 블록 overflow, 모바일 가로 스크롤, 토글 정답 가독성을 Playwright로 검사한다.

### Phase D. Week 10-12 분석·증거·네트워크를 구현

1. AI 답변은 가설, 디버거·로그·PCAP은 관찰이라는 공통 문장을 학습 흐름에 심는다.
2. 포렌식과 PCAP은 제공된 합성 자료만 사용하고, 타인 트래픽 수집법을 안내하지 않는다.
3. 네트워크 보고서에는 필터와 시간 범위를 반드시 기록하게 한다.
4. 각 주차의 화면과 활동 완료 상태가 localStorage에 정상 저장되는지 회귀 검증한다.

### Phase E. Week 13-15 현대 보안 영역을 구현

1. fuzzing은 target/harness/coverage/triage/fix 순서로, CloudGoat은 격리/비용/삭제까지, AI 보안은 모델이 아니라 시스템 경계까지 설명한다.
2. 외부 플랫폼으로 이동시키는 버튼은 준비 체크를 통과한 뒤에만 문맥상 노출한다. 플랫폼 내부에서 원격 공격 자동화를 제공하지 않는다.
3. AI security 종합 활동은 맨 마지막에만 두고, 앞 주차의 최소 권한·신뢰 경계·증거 기록을 다시 사용한다.
4. 전체 build와 전 주차 Playwright smoke test를 수행한다.
5. 실제 구현 상태가 바뀌면 README, `public/sectrack-context.md`, roadmap 설명을 같은 변경에서 갱신해 문서와 코드의 상태가 어긋나지 않게 한다.

## 7. 예상 작업량과 우선순위

계획상 기본 모듈은 78개다. 새 본문은 약 86,000자이며, 그림·질문·캡션·실습 안내를 포함하면 그보다 크다. 따라서 한 번에 얕게 채우지 않고 아래 순서로 구현한다.

1. **Week 03 XSS**: 사용자 불만이 가장 명확하며 이후 웹 보안의 설명 기준을 만든다.
2. **Week 04-05 SQLi/CSRF**: 이미 보강된 뼈대를 내용 밀도와 읽기 구조 기준으로 맞춘다.
3. **Week 06-09 시스템·Pwn 기반**: 앞뒤 의존성이 강하므로 하나의 공통 C 예제로 연결한다.
4. **Week 10-12 AI 검증·암호/포렌식·네트워크**: 증거와 보고서 원칙을 통일한다.
5. **Week 13-15 fuzzing·cloud·AI security**: 실습 안전성, 계정 격리, 신뢰 경계를 가장 엄격히 검토한다.

각 주차는 콘텐츠 작성 후 바로 검토한다. 전체 계획의 마지막까지 기다렸다가 한꺼번에 UI 오류를 찾지 않는다. 콘텐츠 완료 시점마다 다음 세 관점의 피드백을 반영한다.

- **초심 학습자**: 용어의 전제가 빠지지 않았는지, 정답을 보지 않고도 흐름을 따라갈 수 있는지.
- **교육 설계 관점**: 배경→방어→관찰→재시험 순서가 지켜졌는지, 질문이 암기에 머물지 않는지.
- **제품·시각 품질 관점**: 긴 글, 표, 코드, 도식, 토글이 데스크톱과 모바일에서 읽히는지.


## 8. 구현 구조 개정안

### 8.1 현재 고정 factory를 느슨한 module spec으로 바꾼다

모든 모듈에 동일한 block을 자동 삽입하는 factory는 작성 속도는 빠르지만 읽기 리듬을 단조롭게 만든다. factory는 메타데이터 기본값과 안전 검증만 제공하고, 실제 blocks는 모듈 목적에 맞게 저자가 선택한다.

```js
export const moduleSpec = ({
  id,
  title,
  archetype,
  learningQuestion,
  observableOutcome,
  prerequisiteConceptIds = [],
  newConceptIds = [],
  blocks,
  retestMatrix,
  transferGate,
}) => ({
  id,
  title,
  archetype,
  learningQuestion,
  observableOutcome,
  prerequisiteConceptIds,
  newConceptIds,
  blocks,
  retestMatrix,
  transferGate,
})
```

`blocks`에 `question`, `explanation`, `diagram`, `case`, `comparison`, `checkpoint`, `sources`, `summary`를 모두 강제로 넣지 않는다. 대신 스키마 검증기가 서술 유형에 맞는 최소 요구를 확인한다.

### 8.2 기존 block type은 유지하고 variant를 추가한다

대규모 renderer 재작성 없이도 표현 차이를 만들 수 있다.

```js
{ type: 'question', variant: 'lead' | 'prediction' | 'decision' }
{ type: 'explanation', variant: 'narrative' | 'definition' | 'deep-dive' }
{ type: 'diagram', variant: 'flow' | 'boundary' | 'memory' | 'permission' | 'evidence' }
{ type: 'case', variant: 'worked-example' | 'incident' | 'report-review' }
{ type: 'comparison', variant: 'before-after' | 'decision-matrix' }
{ type: 'checkpoint', mode: 'choice' | 'short-answer' | 'ordering' | 'evidence-select' }
{ type: 'practice-link', readiness: [...], expectedEvidence: [...] }
```

추가가 필요한 독립 block은 최소화한다.

- `concept-ref`: 사이트 내부 개념 카드와 최초 정의 위치.
- `evidence-board`: 관찰, 해석, 전제, 미확인, 다음 확인.
- `retest`: 정상·실패·경계값·다른 경로의 비교표.

### 8.3 스키마에서 검사할 교육 품질

```js
validateModule(module) {
  require(module.archetype)
  require(module.learningQuestion)
  require(module.observableOutcome)
  requireUniqueVisibleHeadings(module.blocks)
  requireDefinitionsFor(module.newConceptIds)
  requireInternalReviewLinks(module.prerequisiteConceptIds)
  requireEvidenceBeforeImpactClaim(module.blocks)
  requireRootControlAndRetest(module)
  rejectRequiredExternalDependency(module)
}
```

자동 검사는 글의 품질을 완전히 판단하지 못한다. 대신 빠지기 쉬운 구조적 결함을 차단하고, 문체와 정확성은 사람 리뷰에서 확인한다.

### 8.4 화면 주차와 내부 ID를 데이터에 명시한다

현재의 `화면 주차 ↔ 내부 접두어` 차이는 문서 표만으로 관리하기에 취약하다. 다음 필드를 별도로 둔다.

```js
{
  displayWeek: 3,
  curriculumId: 'xss',
  legacyPrefix: 'w4',
  route: '/learn/week/3'
}
```

테스트는 모든 module, lab, quiz, report template이 동일한 `curriculumId`를 참조하는지 확인한다. 새 콘텐츠 작성자는 화면 번호로 ID를 추측하지 않는다.

## 9. Week 03 기준 모듈의 구체 예시

### 모듈 제목

**검색어는 언제 HTML이 되는가**

- 서술 유형: 흐름 추적형
- 예상 시간: 12~15분
- 선수 개념: URL query, HTTP response, DOM
- 새 개념: source, transform, sink, output context
- 완료 기준: 두 코드와 DOM 결과를 보고 데이터가 코드로 해석되는 실패 지점을 설명한다.

### 도입 장면

검색 화면에 `blue`를 입력하면 `검색어: blue`가 보인다. 그런데 같은 위치에 꺾쇠가 포함된 일반 문장을 넣었을 때 글자가 일부 사라진다면, 입력 검증보다 먼저 **브라우저가 그 값을 어떤 문법으로 해석했는지** 확인해야 한다.

### 정상 모델을 먼저 세운다

검색어는 사용자가 입력한 데이터다. 애플리케이션은 그 값을 읽고 문장을 만들 수 있지만, 브라우저가 HTML 구조로 다시 해석하게 만들 이유는 없다. 일반 텍스트를 표시하는 기능이라면 값은 처음부터 끝까지 text node로 남아야 한다.

```js
const query = new URLSearchParams(location.search).get('q') ?? ''
results.textContent = `검색어: ${query}`
```

- 첫 줄의 URL 값이 **source**다.
- 문자열을 합치는 과정이 **transform**이다.
- `textContent`가 최종 **sink**지만 값을 HTML로 파싱하지 않는 텍스트 전용 sink다.
- 이 기능의 기대 결과는 “사용자가 넣은 글자가 그대로 보인다”다.

### 같은 데이터가 다른 sink에 도달하면

```js
const query = new URLSearchParams(location.search).get('q') ?? ''
results.innerHTML = `검색어: ${query}`
```

여기서 바뀐 것은 입력이 아니라 마지막 한 줄이다. `innerHTML`은 값을 HTML fragment로 파싱한다. 따라서 실패 지점은 “이상한 문자열을 허용한 입력 단계”가 아니라, **일반 텍스트 데이터를 HTML로 해석하는 출력 단계**다.

### 그림: URL에서 DOM까지

`URL query [source] → 문자열 결합 [transform] → innerHTML [interpreting sink] → HTML parser → DOM`

그림에는 `innerHTML`과 HTML parser 사이를 신뢰 경계로 표시한다. 같은 입력이 `textContent`로 가는 안전한 분기에서는 parser를 거치지 않는다는 점을 나란히 보여 준다.

### 읽기 중 판단

> 서버 응답 원문에는 고유 마커가 없고, 실행 후 DOM에만 마커가 나타났다. 이 사실만으로 반사형 XSS라고 확정할 수 있는가?

**해설**: 확정할 수 없다. 서버 응답과 클라이언트 JavaScript의 source·transform·sink를 분리해서 보아야 한다. 실행 후 DOM에서만 값이 생겼다면 DOM 기반 경로를 우선 조사하지만, 데이터가 서버 응답의 JSON이나 저장 데이터에서 왔을 가능성도 추가로 확인한다.

### 영향과 전제

코드가 브라우저에서 실행되었다는 관찰과 실제 영향을 분리한다. 영향은 해당 사용자의 권한, 페이지 기능, 접근 가능한 데이터, `HttpOnly` 같은 보호 속성, CSP와 다른 브라우저 통제에 따라 달라진다. `HttpOnly`는 일부 쿠키의 JavaScript 읽기를 제한하지만 해석형 sink 자체를 텍스트 sink로 바꾸지는 않는다.

### 수정과 재시험

1. HTML이 필요 없는 위치는 `textContent`로 바꾼다.
2. 제한된 서식 HTML이 정말 필요하면 승인된 sanitization policy를 사용하고 허용 요소·속성을 문서화한다.
3. 프레임워크의 raw HTML escape hatch를 검색해 같은 경로가 남아 있는지 확인한다.
4. CSP는 남은 결함의 영향을 줄이는 보완 통제로 검토하되 원인 수정으로 기록하지 않는다.

| 재시험 범주 | 입력 또는 상태 | 기대 결과 |
| --- | --- | --- |
| 정상 | 일반 한글·영문 검색어 | 글자가 그대로 표시되고 검색 기능 유지 |
| 문법 문자 | 꺾쇠·따옴표가 포함된 일반 텍스트 | DOM 구조가 늘지 않고 문자로 표시 |
| 경계 | 빈 값·긴 값·다국어 | 안전한 오류 또는 정상 표시, 레이아웃 유지 |
| 다른 경로 | 자동완성·최근 검색어·저장된 검색어 | 동일한 텍스트 출력 정책 적용 |

### 다음 단계 준비 체크

- source, transform, sink를 코드에서 각각 표시할 수 있다.
- HTML body와 attribute처럼 output context가 달라지면 방어도 달라지는 이유를 설명할 수 있다.
- “실행됨”과 “어떤 영향이 확인됨”을 다른 문장으로 쓸 수 있다.
- 수정 후 정상 기능과 실패 조건을 함께 재시험할 수 있다.

이 네 항목을 충족한 뒤에만 내부 XSS sandbox와 허가된 외부 학습 단원으로 이동한다.
