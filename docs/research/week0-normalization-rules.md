# WEEK 0 직무 정규화 규칙

## 네 개의 데이터 층

직무 탐색기의 모든 정보는 다음 중 하나로 구분한다.

| 층 | 화면 라벨 | 의미 |
| --- | --- | --- |
| 공고 원문 사실 | 공고 직접 확인 | handoff에 보존된 공고의 업무, 요건, 우대, 도구, 협업 조직 |
| SecTrack 정규화 | SecTrack 분류 | 서로 다른 공고 제목을 비교하기 위해 연결한 분야·직무군·세부 직무 |
| 업무 문장 기반 도출 | 본문 기반 추론 | 공고 업무에서 학습자가 준비할 수 있는 산출물 후보 |
| 일반 직무 설명 | 직무 일반 설명 | 특정 공고의 사실이 아니라 역할을 이해하기 위한 일반 설명 |
| 리서치 역할 목록 | 리서치 보고서의 대표 역할 | 분야별 역할 분화를 보여주되, 개별 공고·공식 체계 근거가 충분하지 않은 역할 |

## 매핑 규칙

1. 공고 원문 제목과 업무 문장을 보존한다. 표현을 더 그럴듯하게 확장하지 않는다.
2. 하나의 공고는 여러 세부 직무에 연결할 수 있다. 연결에는 제목·업무·요건 중 어떤 근거를 썼는지와 신뢰도를 둔다.
3. 분야는 기술·시스템의 대상 범위다. 직무군은 조직 안에서 수행하는 업무 기능이다. 세부 직무는 비교 단위인 역할이다.
4. `직접` 근거가 없는 세부 직무는 `인접 공고 근거` 또는 `직무 일반 설명`으로 표시한다.
5. 경력, 근무지, 고용 형태, 도구, 표준은 원문 보존 범위 안에서만 표시한다. 빈 값은 "미확인"으로 둔다.
6. 공개 URL과 지원 URL은 제공된 경우에만 표시한다. 앱에서 생성하거나 추론하지 않는다.
7. `isCurrent`, `checkedDate`는 확인 근거가 없는 한 `null`이다. 화면은 "현재 상태 미확인"으로 표시한다.
8. 분야별 대표 역할은 운영자가 제공한 직무군 목록을 그대로 사용한다. 역할 수는 분야별로 다르며, 채용 수요 순위가 아니다. 상세 근거 카드와 구분한다.
9. `Tier 1·2·3`, `Junior·Senior`, 교대조 같은 숙련도·조직 운영 단계는 독립 직무로 세지 않는다. 예를 들어 SOC는 `SOC Analyst`로 정규화하고 Tier는 역할 설명 안의 운영 맥락으로 둔다.
10. 같은 역할이 내부 보안 운영과 보안 제품·플랫폼 개발 양쪽에서 수행될 수 있으면, 역할을 중복 배치하지 않는다. 주 소속 분야 하나와 연결 분야·조직 맥락을 별도로 기록한다.

## 역할 데이터 규칙

- `실제로 하는 일`: 공고 직접 근거가 있을 때만 직접 근거 라벨을 사용한다.
- `대표 산출물`: 업무 문장에서 도출했으면 추론 라벨을 사용한다.
- `신입·초중급 기반`, `경력에서 확장되는 책임`: 일반 직무 설명으로 분리한다.
- Cloud/IAM 12개와 DFIR 10개 역할은 역할 단위로 유지한다. 넓은 직무명 하나로 합쳐 비교 정보를 잃지 않는다.
- 개인 보안 지도는 관심 분야 2개, 세부 직무 열람 4개, 관심 직무 2개, 포트폴리오 후보 2개를 조건으로 한다. 선택값은 브라우저 localStorage에 저장하며 JSON으로 내보낼 수 있다.
- 관계도는 하나의 캔버스로 유지한다. 전문 분야와 보고서에서 확인한 교차 연결을 기본으로 두고, 분야 선택 시 같은 캔버스 안에서 해당 분야 노드가 `분야 → 직무군 → 제공된 역할 목록`으로 확장된다. 역할 선택 시 연결 분야와 제품·플랫폼 개발 맥락을 강조한다.
