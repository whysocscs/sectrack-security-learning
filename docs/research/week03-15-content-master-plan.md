# SecTrack Week 03-15 콘텐츠 심화 마스터 플랜

작성일: 2026-07-13
상태: 조사 및 구현 계획 초안. 이 문서는 콘텐츠가 이미 보강되었다는 완료 보고서가 아니다.

## 1. 목적과 적용 범위

이 계획의 대상은 SecTrack 화면에서 보이는 **Week 03부터 Week 15까지**다. 목표는 짧은 정의와 문제 목록을 늘리는 것이 아니라, 보안을 처음 배우는 1학년이 다음 질문에 자기 말로 답할 수 있을 정도의 읽기 자료를 만드는 것이다.

1. 이 기술 또는 시스템은 원래 무엇을 하기 위해 존재하는가?
2. 데이터와 권한, 실행 흐름 중 어디에서 경계가 깨지는가?
3. 그 결함은 어떤 조건에서 실제 문제가 되며, 영향은 어디까지 가능한가?
4. 개발자와 운영자는 어떤 설계와 검증으로 이를 줄이는가?
5. 실습, 취약점 보고서, 재시험에서 무엇을 사실로 기록해야 하는가?

범위에는 보안의 배경, 방어 관점, 안전한 합성 예시, 로컬 실습, 외부 학습으로 넘어가는 다리가 포함된다. 승인되지 않은 대상에 대한 공격 절차, 원격 표적 자동화, 실제 계정·세션·키 탈취 예제, 재현 가능한 침해 지침은 포함하지 않는다.

## 2. 참고 글 구조 스크랩과 채택 기준

### 2.1 사용자가 준 XSS 참고 글

| 자료 | 확인한 구성 | SecTrack에 채택할 점 | 채택하지 않을 점 |
| --- | --- | --- | --- |
| [XSS의 개념과 종류 - shine's dev log](https://ddongwon.tistory.com/130) | 개념, 등장 주체, 반사형·저장형·DOM 기반 유형, 각 유형의 단계 흐름, 방어 순서로 길게 전개한다. 그림 다음에 흐름을 번호로 다시 푼다. | 한 번의 정의로 끝내지 않고, **브라우저가 어느 순간 데이터를 해석하는지**를 그림과 단계 설명으로 반복한다. 유형별로 입력이 들어오는 위치와 피해자에게 닿는 경로를 분리한다. | 기술 근거와 방어 규칙은 개인 블로그에 의존하지 않는다. 세션 탈취를 모든 XSS의 필연적 결과처럼 쓰지 않고, `HttpOnly`, 사용자 권한, Same-Origin Policy, 기능 범위에 따른 조건을 함께 쓴다. |
| [나무위키 XSS](https://namu.wiki/w/XSS) | 사용자가 제시한 폭넓은 개요 참고 자료다. 자동 수집 도구에서는 이 URL을 열 수 없어 본문을 스크랩하거나 사실 근거로 사용하지 않았다. | 초심자 문서도 "정의-유형-사례-방어"를 한 화면에서 훑을 수 있어야 한다는 **범위 점검용**으로만 둔다. | 검증하지 못한 본문, 사례, 표현을 복사하거나 출처로 인용하지 않는다. |

위 참고 글에서 가져갈 것은 문장이나 코드가 아니라 **긴 스크롤에서도 길을 잃지 않는 설명 순서**다. 각 핵심 개념은 `왜 필요한가 → 어떻게 동작하는가 → 어디가 깨지는가 → 무엇이 가능한가 → 어떻게 막고 다시 확인하는가` 순서로 쓴다.

## 3. 모든 주차에 적용할 콘텐츠 설계 규칙

### 3.1 한 모듈의 기본 뼈대

각 모듈은 독립된 블로그 글처럼 읽히되, 서로 연결되는 다음 순서를 지킨다.

1. **상황 한 줄**: 학습자가 이미 아는 서비스나 프로그램의 문제로 시작한다.
2. **배경 원리**: 용어를 먼저 정의하고, 데이터·제어 흐름·신뢰 경계를 그림으로 설명한다.
3. **문제의 발생 지점**: 입력, 변환, 권한 검사, 출력, 메모리 접근 중 어느 지점이 실패했는지 표시한다.
4. **영향과 전제**: 가능한 영향, 필요한 권한, 보호 장치가 있는 경우 달라지는 점을 분리한다. 과장하지 않는다.
5. **방어와 운영 확인**: 코드·설정·권한·로그·테스트로 나누어 설명한다.
6. **안전한 예시와 관찰**: 합성 데이터 또는 내부 샌드박스에서 정상/취약/수정 후 상태를 비교한다.
7. **Question**: 정답을 접을 수 있는 질문 두 개 이상으로, 단순 암기보다 판단을 묻는다.
8. **재시험 또는 외부 학습 연결**: 무엇을 확인한 뒤 Dreamhack, Bandit, Fuzzing101, CloudGoat 같은 허가된 과정으로 넘어갈지 제시한다.

### 3.2 분량과 화면 구성의 공통 기준

- 본문은 주차당 **7,000-10,000자**를 기본으로 한다. 비교적 복잡한 Week 03, 06, 09, 12, 15는 9,000-12,000자까지 허용한다. 표, 코드 캡션, 질문, 출처는 본문 분량에서 제외한다.
- 모듈 하나는 보통 **1,000-1,500자**, 긴 원리 설명 모듈은 최대 1,800자로 제한한다. 이보다 길어지면 "다음 그림" 또는 "다음 실패 지점"으로 분할한다.
- 주차마다 최소 **4개 시각 자료**를 둔다. 실제 스크린샷이 필요 없는 경우에는 HTML/CSS 기반 흐름도, 메모리·패킷·권한 관계도처럼 화면 크기에 깨지지 않는 도식으로 만든다.
- 주차마다 최소 **2개 오해 바로잡기**, **2개 토글형 Question**, **1개 안전한 내부 관찰 활동**, **1개 외부 과정으로 이어지는 준비 체크**를 둔다.
- 표는 3열을 넘기지 않는다. 휴대폰에서 가로 스크롤이 필요한 정보는 용어 카드나 접이식 목록으로 나눈다.
- 코드·명령·HTTP·패킷은 "무엇을 보아야 하는지"를 줄 단위 주석으로 붙인다. 보안 문제를 재현하는 문자열이나 원격 대상 명령은 넣지 않는다.

### 3.3 안전성과 보고서 원칙

- 실습은 로컬, 의도적으로 취약하게 설계된 내부 화면, 또는 명확히 허가된 교육 플랫폼으로 제한한다.
- 취약점 보고서는 `관찰 사실`, `영향 판단`, `전제 조건`, `개선안`, `재시험 결과`를 분리한다. 추측을 사실처럼 쓰지 않는다.
- 민감 정보는 항상 가상값으로 사용한다. 실습 로그에는 쿠키, 토큰, 실제 계정, 개인 정보, 조직 주소를 보관하지 않는다.
- "방어"는 필터 하나나 제품 하나로 끝내지 않는다. 근본 원인, 보완 통제, 탐지·복구의 역할을 구분한다.

## 4. Week 03-15 주차별 구현 명세

### Week 03. XSS: 브라우저가 데이터를 코드로 해석할 때

**학습 완료 기준**: 학습자는 반사형, 저장형, DOM 기반 XSS를 입력 위치가 아니라 **데이터가 위험한 출력 지점(sink)에 도달하는 경로**로 구분하고, HTML·속성·URL·JavaScript 컨텍스트마다 방어가 달라진다고 설명할 수 있다. 또한 보고서에서 "실행되었다"는 관찰과 "어떤 영향이 가능한가"라는 판단을 분리해 쓴다.

| 모듈 | 구체적으로 가르칠 내용 | 표현·실습 방식 | 목표 분량 |
| --- | --- | --- | --- |
| 03-1. 브라우저는 왜 문자열을 해석하는가 | HTML, DOM, JavaScript, origin, 렌더링의 역할. 서버 응답과 브라우저가 이후 DOM을 바꾸는 일을 분리한다. `<script>` 자체를 모르던 학습자도 태그·속성·텍스트 노드의 차이를 따라오게 한다. | 요청→응답→DOM 파싱→화면 표시 4단계 그림. 모든 위험 문자열은 `[사용자 입력]`으로 치환한다. | 1,500자 |
| 03-2. Source, transform, sink | URL·폼·저장 데이터가 source가 될 수 있고, 조합·템플릿·클라이언트 코드가 변환 단계이며, `innerHTML`류의 해석 지점이 sink가 되는 구조. 반사형·저장형·DOM 기반의 차이를 같은 도식 위에서 비교한다. | 데이터 흐름 지도와 3열 비교표. 안전한 `textContent` 대 해석형 출력의 합성 코드 비교. | 1,600자 |
| 03-3. 출력 컨텍스트가 방어를 바꾸는 이유 | HTML 본문, 인용된 속성, URL 값, JavaScript 문자열, CSS 값은 브라우저의 파서가 다르다. 프레임워크 기본 escaping, 컨텍스트별 encoding, 허용 HTML이 필요한 경우 sanitization을 구별한다. | 컨텍스트 색상 지도와 "이 출력 위치에서는 무엇을 데이터로 취급해야 하는가" 카드. | 1,700자 |
| 03-4. 왜 문제이고 무엇이 가능한가 | 피해자 브라우저의 동일 출처 문맥에서 UI 조작, 사용자의 권한으로 수행되는 동작, 민감 데이터 노출 같은 영향을 조건부로 설명한다. `HttpOnly`가 일부 쿠키 접근을 줄이지만 XSS 실행 자체를 해결하지 않는다는 점도 포함한다. | 영향 행렬: 사용자 권한 / 기능 / 보호 장치 / 가능한 결과. 과장된 "쿠키 탈취 = 모든 XSS" 오해 정정. | 1,300자 |
| 03-5. 설계·구현·브라우저의 방어 계층 | 기본 템플릿 escaping, 안전한 sink, 제한된 HTML sanitization, URL allowlist, CSP와 Trusted Types의 보완 역할, 라이브러리·프레임워크 escape hatch 점검. CSP·WAF·입력 차단만으로 해결된다는 오해를 바로잡는다. | 방어 계층 그림과 수정 전/후 코드 리뷰 카드. 실제 우회 문자열은 사용하지 않는다. | 1,700자 |
| 03-6. 보고서를 읽고 쓰는 법 | 제목, 범위, 재현 전제, source/sink/context, 관찰 결과, 영향, 원인, 권고안, 수정 후 재시험. 공개 보고서는 "공격 코드"보다 사실을 재현 가능하게 남기는 문서라는 점을 설명한다. | 합성 XSS 보고서의 좋은 문장/나쁜 문장 비교. | 1,300자 |
| 03-7. 수정 후 무엇을 다시 확인하는가 | 정상 텍스트가 깨지지 않는지, 모든 렌더링 경로가 같은 보호를 적용하는지, 허용 HTML 정책이 필요한 기능을 망가뜨리지 않는지, DOM 경로가 남지 않았는지 확인한다. | 샌드박스의 source/sink 추적 활동, Question 3개, Dreamhack으로 넘어가기 전 준비 체크. | 1,100자 |

주차는 독립된 용어 사전이 아니다. 콘텐츠 안에 아래 연결을 명시적으로 넣는다.

| --- | --- |

## 6. 구현 단계와 검증 게이트

### Phase A. Week 03 XSS를 기준 품질로 재구성

1. `w4-*` 콘텐츠를 7개 모듈 순서로 교체 또는 추가한다.
2. source→transform→sink, 출력 컨텍스트, 방어 계층, 보고서·재시험을 각각 독립 block으로 만든다.
3. 기존 내부 XSS 실습이 외부 통신, 실제 credential, 공격 payload를 쓰지 않는지 다시 확인한다.
4. 콘텐츠 스키마 테스트, XSS 안전성 테스트, 데스크톱·모바일 Playwright 화면 검증, production build를 실행한다.

### Phase B. Week 04-05 웹 보안의 깊이와 연결 보정

1. SQLi와 CSRF의 기존 상세 블록을 위 표의 목표 분량과 용어 수준에 맞춰 확장한다.
2. SQLi의 parameterization과 CSRF의 token은 "기능 이름"이 아니라 "서버가 확인하는 사실" 중심으로 재작성한다.
3. XSS가 있으면 CSRF 통제가 약화될 수 있다는 관계를 한 번만 정확히 연결하고, 과도하게 반복하지 않는다.
4. 각각 내부 관찰 활동, Question, 보고서 템플릿을 테스트한다.

### Phase C. Week 06-09 시스템 기반을 누적형으로 구현

1. 같은 작은 C 프로그램을 C 문법→메모리→어셈블리→GDB→메모리 안전성으로 재사용한다.
2. 주차별 화면에서 같은 그림을 복붙하지 않고, 이전 그림의 일부를 다시 보여 주며 새 관찰 요소만 강조한다.
3. BOF는 방어와 원인 분석을 중심으로 다루며, 실제 침해용 exploit tutorial로 바꾸지 않는다.
4. 코드 블록 overflow, 모바일 가로 스크롤, 토글 정답 가독성을 Playwright로 검사한다.

### Phase D. Week 10-12 분석·증거·네트워크를 구현

1. AI 답변은 가설, 디버거·로그·PCAP은 관찰이라는 공통 문장을 학습 흐름에 심는다.
2. 포렌식과 PCAP은 제공된 합성 자료만 사용하고, 타인 트래픽 수집법을 안내하지 않는다.
3. 네트워크 보고서에는 필터와 시간 범위를 반드시 기록하게 한다.
4. 각 주차의 화면과 활동 완료 상태가 localStorage에 정상 저장되는지 회귀 검증한다.

### Phase E. Week 13-15 현대 보안 영역을 구현

1. fuzzing은 target/harness/coverage/triage/fix 순서로, CloudGoat은 격리/비용/삭제까지, AI 보안은 모델이 아니라 시스템 경계까지 설명한다.
2. 외부 플랫폼으로 이동시키는 버튼은 준비 체크를 통과한 뒤에만 문맥상 노출한다. 플랫폼 내부에서 원격 공격 자동화를 제공하지 않는다.
3. AI security 종합 활동은 맨 마지막에만 두고, 앞 주차의 최소 권한·신뢰 경계·증거 기록을 다시 사용한다.
4. 전체 build와 전 주차 Playwright smoke test를 수행한다.

## 7. 예상 작업량과 우선순위

계획상 기본 모듈은 78개다. 새 본문은 약 86,000자이며, 그림·질문·캡션·실습 안내를 포함하면 그보다 크다. 따라서 한 번에 얕게 채우지 않고 아래 순서로 구현한다.

1. **Week 03 XSS**: 사용자 불만이 가장 명확하며 이후 웹 보안의 설명 기준을 만든다.
2. **Week 04-05 SQLi/CSRF**: 이미 보강된 뼈대를 내용 밀도와 읽기 구조 기준으로 맞춘다.
3. **Week 06-09 시스템·Pwn 기반**: 앞뒤 의존성이 강하므로 하나의 공통 C 예제로 연결한다.
4. **Week 10-12 AI 검증·암호/포렌식·네트워크**: 증거와 보고서 원칙을 통일한다.
5. **Week 13-15 fuzzing·cloud·AI security**: 실습 안전성, 계정 격리, 신뢰 경계를 가장 엄격히 검토한다.

각 주차는 콘텐츠 작성 후 바로 검토한다. 전체 계획의 마지막까지 기다렸다가 한꺼번에 UI 오류를 찾지 않는다. 콘텐츠 완료 시점마다 다음 세 관점의 피드백을 반영한다.

- **초심 학습자**: 용어의 전제가 빠지지 않았는지, 정답을 보지 않고도 흐름을 따라갈 수 있는지.
- **교육 설계 관점**: 배경→방어→관찰→재시험 순서가 지켜졌는지, 질문이 암기에 머물지 않는지.
- **제품·시각 품질 관점**: 긴 글, 표, 코드, 도식, 토글이 데스크톱과 모바일에서 읽히는지.
